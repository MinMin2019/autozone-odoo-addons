# คู่มือผู้ดูแลระบบ — Access Control (Role Builder + Warehouse Scope)

> สำหรับทีม IT ผู้ดูแลสิทธิ์การใช้งาน Odoo ของบริษัท
> โมดูล: `custom_access_role_builder` + `custom_warehouse_scope` · Odoo 18 Enterprise

---

## 1. แนวคิดของระบบ (อ่านก่อนใช้งาน)

นโยบายของบริษัทคือ **แต่ละคนเห็นเฉพาะงานของตัวเอง + ข้อมูลเท่าที่จำเป็น** ระบบนี้จึงคุมสิทธิ์ 2 มิติพร้อมกัน:

| มิติ | คุมด้วย | ตัวอย่าง |
|---|---|---|
| **ชนิดเอกสาร** (ทำงานอะไรได้บ้าง) | **Role** (โมดูล Role Builder) | บัญชี AP เห็นเฉพาะ Bill + Payment |
| **ขอบเขตข้อมูล** (เห็นข้อมูลของสาขาไหน) | **Warehouse Scope** (ตั้งรายคนที่ user) | พนักงานสาขา 3 เห็นเฉพาะสต๊อก/ใบย้ายของสาขา 3 |

### Role ทำงานยังไง (หลังกด Apply)

1. ระบบสร้าง **กลุ่มสิทธิ์ (res.groups)** ให้อัตโนมัติ — แยกเป็น "อิฐ" (สิทธิ์ 1 ก้อน = model + ระดับ + เงื่อนไขข้อมูล) แล้วประกอบเป็น role
2. สร้าง **เมนูชุดใหม่ (whitelist)** ให้เห็นเฉพาะเมนูที่ role นั้นได้รับ — user จะเห็นไอคอนแอป (เช่น Accounting) แต่ข้างในมีเฉพาะเมนูที่อนุญาต
3. ถ้าเปิด **strict (Exclusive Membership)** ระบบจะถอดกลุ่มมาตรฐานของ Odoo ออกจาก user ให้เหลือแค่ Internal User + กลุ่มของ role → เมนูมาตรฐานหายหมด เหลือแต่ whitelist
4. **Foundation mirror**: ระบบแอบให้สิทธิ์ "อ่าน" model สนับสนุนของแอปนั้น (copy จากกลุ่มมาตรฐาน) เพื่อให้หน้าจอเปิดได้ไม่ติด AccessError โดยที่ user **ไม่ได้ถือกลุ่มมาตรฐานจริง** (เมนูมาตรฐานจึงยังซ่อนอยู่)

> **ผู้ใช้ที่เป็น Admin/Settings จะเห็นทั้งเมนูมาตรฐานและเมนู whitelist ซ้อนกัน — เป็นเรื่องปกติ** เพราะ admin ถือทุกกลุ่ม การทดสอบต้องใช้ user สะอาด (ดูข้อ 5)

## 2. เมนูในแอป Access Control

### 2.1 Roles — ใช้ประจำ ⭐
หน้าหลักสำหรับสร้าง/แก้/Apply role (ขั้นตอนละเอียดดูข้อ 4)

### 2.2 Users
ทางลัดไปหน้า Users ใช้ทำ 2 อย่าง:
- ตั้ง **Warehouse Scope** (แท็บ Warehouse Scope ในฟอร์ม user) — เลือกคลังที่ user คนนั้นเห็นข้อมูลได้
- ดูว่าแต่ละ user ถือกลุ่มอะไรอยู่

> ⚠️ **ห้ามใส่ role ให้ user จากหน้า Users** — ให้ไปเพิ่มที่แท็บ *Users with this Role* ในฟอร์ม Role แล้วกด Apply เท่านั้น ไม่งั้นระบบ sync สมาชิกไม่ถูก

### 2.3 Catalog (กลุ่มเมนูจัดการแคตตาล็อก)

| เมนู | ทำอะไร | ใช้เมื่อไหร่ |
|---|---|---|
| **Menu Catalog** | รายการ "เมนู/เอกสาร" ทั้งหมดที่หยิบไปประกอบ role ได้ | เปิดดู/แก้รายละเอียดรายการ เช่น เติม Domain, Extra Read Models |
| **Import from App Menu** | สแกนเมนูของแอปที่เลือก แล้วสร้างรายการ catalog ให้อัตโนมัติ | เมื่อ catalog ยังไม่มีเมนูของแอปนั้น หรือมีไม่ครบ (เช่น รายงานบัญชี) |
| **Reload Catalog from CSV** | โหลดรายการจากไฟล์ `master_matrix.csv` + `custom_catalog.csv` ใหม่ | หลังแก้ไฟล์ CSV ต้นทาง |

### 2.4 Maintenance (เครื่องมือซ่อมบำรุง — นานๆ ใช้ที)

| เมนู | ทำอะไร | ใช้เมื่อไหร่ |
|---|---|---|
| **Rebuild All Menus** | ลบเมนู whitelist ที่ generate ทั้งหมด แล้วสร้างใหม่จากทุก role ที่ Applied | เมนูเพี้ยน/ซ้ำ/ค้าง — กดปุ่มนี้ก่อนเสมอ **ห้ามลบเมนูด้วย SQL** |
| **Harden Standard Menus** | ใส่กลุ่มกั้น root menu มาตรฐานที่เปิดกว้าง | หลังติดตั้งโมดูลใหม่ที่เมนูรั่วถึงพนักงานทั่วไป |
| **Remove Unused Groups** | เก็บกวาดกลุ่ม/เมนู/action ที่ role ต้นทางถูกลบไปแล้ว | หลังลบ role ทิ้ง |
| **Reset Default User Template** | ล้างแม่แบบสิทธิ์ `base.default_user` (ต้นแบบที่ Odoo ก็อปให้ user ใหม่ทุกคน) ให้เหลือ Internal User อย่างเดียว | ครั้งแรกหลังติดตั้ง และทุกครั้งที่สงสัยว่า user ใหม่เกิดมาพร้อมสิทธิ์เกิน (เคยพบ template ถูกบันทึกไว้ ~80 กลุ่มรวม Administrator แทบทุกแอป) |
| **Export Roles** | บันทึก role ที่เลือก (บรรทัดสิทธิ์/ระดับ/domain/รายชื่อ user) เป็นไฟล์ JSON — จับคู่ catalog ด้วยชื่อ ไม่ผูก id ของฐาน | ก่อน deploy production หรือสำรอง role config |
| **Import Roles** | อ่านไฟล์จาก Export Roles: role เดิม (จับด้วย code) ถูกอัปเดตทับ, role ใหม่ถูกสร้าง, บรรทัดถูกแทนที่ทั้งชุดตามไฟล์, user ผูกตาม login; catalog/login ที่หาไม่เจอ = ข้าม + รายงาน **ไม่ Apply ให้อัตโนมัติ** — ตรวจแล้วกด Apply เองทีละ role | บนฐานปลายทาง (production) หลังติดตั้งโมดูล + เตรียม catalog แล้ว |

**ขั้นตอนแนะนำตอนสร้าง user ใหม่:** กด Reset Default User Template ให้เรียบร้อยก่อน (ทำครั้งเดียวพอ) → สร้าง user ตามปกติ (จะได้แค่ Internal User) → เพิ่มชื่อเข้า role ที่แท็บ **Users with this Role** → ติ๊ก Exclusive Membership → **Apply** — ห้ามติ๊กสิทธิ์รายแอปบนฟอร์ม user เอง

## 3. ความหมายของ Field

### 3.1 ฟอร์ม Role

| Field | ความหมาย |
|---|---|
| **Name** | ชื่อ role เช่น "บัญชี AP สาขา" — ใช้เป็นชื่อกลุ่มสิทธิ์ด้วย |
| **Code** | รหัสถาวรของ role (ตั้งครั้งเดียว ห้ามเปลี่ยนหลัง Apply) ใช้ผูก group/rule ภายใน |
| **Include Foundation** | เปิดไว้เสมอ (ค่าปกติ) — ให้สิทธิ์อ่านพื้นฐาน + mirror ของแอปที่ role แตะ เพื่อให้หน้าจอเปิดได้ |
| **Exclusive Membership** (strict) | ตอน Apply จะถอดกลุ่มมาตรฐาน/technical ออกจาก user ในแท็บ Users เหลือ Internal User + กลุ่มของเรา → ใช้กับพนักงานทั่วไป **อย่าใช้กับ admin** |
| **Last Apply** | เวลา Apply ล่าสุด (ว่าง = ยังไม่เคย หรือถูก Revoke แล้ว) |
| **Role Group** | กลุ่มสิทธิ์ที่ระบบสร้างให้ (อ่านอย่างเดียว) |
| **State** | Draft = ยังไม่มีผล / Applied = สิทธิ์+เมนูถูกสร้างแล้ว |

**ปุ่มบน header:**
- **Apply — Build Access**: สร้าง/อัปเดตสิทธิ์+เมนูทั้งหมดจาก role นี้ (กดซ้ำได้ ปลอดภัย เป็นการ sync)
- **Revoke Generated Access**: ถอนสิทธิ์+เมนูของ role นี้ กลับเป็น Draft (user ในแท็บยังอยู่ แต่ไม่มีสิทธิ์จนกว่าจะ Apply ใหม่)

**แท็บ Access Lines** (รายการสิทธิ์ของ role):

| Field | ความหมาย |
|---|---|
| **Menu / Document** | เลือกรายการจาก catalog |
| **App / Data Model** | มาจาก catalog อัตโนมัติ (อ่านอย่างเดียว) |
| **Access Level** | `—` ไม่ให้สิทธิ์ · `R` อ่าน · `RC` อ่าน+สร้าง (append-only) · `E` อ่าน+แก้ · `C` อ่าน+แก้+สร้าง · `F` เต็ม (ลบได้) |

> **ระดับ `RC` (อ่าน+สร้าง):** เพิ่ม record ใหม่ได้ แต่**ย้อนแก้ของเดิมไม่ได้เลย** — เซฟฟอร์มรอบแรกผ่านแล้ว การเซฟซ้ำ/แก้คำผิด/เปลี่ยนสถานะ (เช่นยืนยันเอกสาร) จะถูกบล็อกทั้งหมด เหมาะกับงานสมุดบันทึกแบบห้ามแก้ย้อนหลัง ถ้า user แจ้งว่าติดตรงนี้ = พฤติกรรมที่ตั้งใจ ให้ปรึกษาผู้กำหนดสิทธิ์ก่อนเปลี่ยนระดับ (บรรทัดเอกสารในโมเดลลูกก็เป็น append-only ตามด้วย) |
| **Needs rule** | ติ๊ก = model นี้ใช้ร่วมกับเมนูอื่น ต้องมี Domain ตัดข้อมูล (ดูข้อ 6.2) |
| **Domain (override)** | เงื่อนไขตัดข้อมูล — copy มาจาก catalog อัตโนมัติ แก้เฉพาะเมื่อ role นี้ต้องการเงื่อนไขต่างจากปกติ |

ปุ่ม **Add Multiple...** = เลือกหลายรายการเข้า role ทีเดียว (ติ๊กจากรายการ แล้ว Add Selected) — รายการที่ role นี้หยิบไปแล้วจะ**ไม่โผล่ในหน้าเลือก** (ดูของที่มีแล้วได้จากตาราง Access Lines)

**เมนูซ้อนหลายชั้น:** รายการที่มาจาก Import from App Menu พก Menu Path มาด้วย เมนู whitelist จะซ้อนชั้นตามของจริงอัตโนมัติ เช่น หยิบ ใบสำคัญรับ (RV) + ใบสำคัญทั่วไป (JV) → ได้ Accounting > Accounting > Vouchers (สมุดรายวัน) > RV/JV โดยหัวข้อ Vouchers เป็นชั้นพับที่ระบบสร้างให้เอง **ข้อควรระวัง:** อย่าหยิบ entry แม่ ("Vouchers (สมุดรายวัน)") พร้อมลูก (RV/JV) ใน role เดียว จะได้ชื่อซ้ำสองอันข้างกัน — เลือกทางเดียว

**แท็บ Users with this Role**: รายชื่อ user ที่ถือ role นี้ — **เพิ่ม/ลบ user ที่นี่เท่านั้น** แล้วกด Apply เพื่อ sync

**แท็บ Last Apply Summary**: สรุปผลการ Apply ครั้งล่าสุด (สร้างอะไรไปกี่รายการ มี conflict ไหม)

### 3.2 ฟอร์ม Catalog Entry

| Field | ความหมาย |
|---|---|
| **Menu / Document** | ชื่อเมนู (ตรงกับที่ user จะเห็นใน whitelist) |
| **App** | แอปเจ้าของ (Accounting, Inventory, ...) — เป็นชื่อไอคอนแอปใน whitelist |
| **Section (Main)** | หมวดในแอป ใช้จัดชั้นเมนูเมื่อไม่มี Menu Path |
| **Menu Path** | path เมนูเต็ม (จาก Import) เช่น `Accounting / Vendors / Bills` — ใช้ซ้อนเมนู whitelist ให้เหมือนของจริง |
| **Data Model** | model ข้อมูลที่เมนูนี้เปิด (เช่น `account.move`) — **ต้องมีเสมอ** ไม่งั้นใช้กับ role ไม่ได้ |
| **Existing Action** | ชี้ action เดิมของโมดูล (act_window) — ใช้ context/view เดิมทั้งชุด แทนการ generate ใหม่ |
| **Client Action** | สำหรับหน้าจอแบบ client action เช่น รายงานบัญชี Enterprise (P&L, งบดุล) — ต้องเติม Data Model เองด้วย (ปกติ = `account.report`) |
| **View Mode** | มุมมองของ action ที่ generate เช่น `list,form` (ไม่ใช้เมื่อมี Existing/Client Action) |
| **Needs Record Rule** | ติ๊ก = model ใช้ร่วมหลายเมนู ต้องใส่ Domain ตัดข้อมูล |
| **Domain (record rule)** | เงื่อนไขตัดข้อมูล เช่น `[('move_type','=','in_invoice')]` = เมนูนี้แสดงเฉพาะ Bill และ**สร้าง/แก้/ลบได้เฉพาะ** record ที่เข้าเงื่อนไข (การ "อ่าน" ไม่ถูกบล็อก — ตั้งใจ เพื่อไม่ให้ rule ลามไปหักการอ่าน model ที่เกี่ยวพันกัน เช่น res.users←res.partner จนล็อกอินไม่ได้) |
| **Domain hint (from CSV)** | ข้อความต้นทางจาก CSV ก่อนแปลงเป็น domain (อ้างอิงเฉยๆ) |
| **Default Level** | ระดับสิทธิ์เริ่มต้นเวลาเพิ่มรายการนี้เข้า role |
| **Extra Read Models** | model เสริมที่ให้สิทธิ์ "อ่าน" พ่วงไปด้วย — ใช้แก้ AccessError จาก smart button / ลิงก์ข้าม model (ดูข้อ 6.1) |
| **Needs Review** | ระบบเติมข้อมูลให้ไม่ครบ (มักขาด Data Model) — ต้องเปิดมาเติมก่อนถึงจะใช้ได้ |
| **Active** | ปิด = ซ่อนจากตัวเลือก (ไม่ลบ) |
| **Note** | บันทึกช่วยจำ |

### 3.3 หน้า User — แท็บ Warehouse Scope (โมดูล custom_warehouse_scope)

| Field | ความหมาย |
|---|---|
| **Warehouse Unrestricted** | ติ๊ก = ไม่จำกัดคลัง (เห็นทุกคลัง) ใช้กับผู้จัดการ/ส่วนกลาง |
| **Allowed Warehouses** | คลังที่ user เห็นข้อมูลได้ — **ว่าง = ไม่ถูกจำกัด** (ปลอดภัยตอน rollout) ใส่คลัง = เห็นเฉพาะคลังนั้น |

ครอบคลุม: สต๊อกคงเหลือ, ใบย้าย/รับ/ส่ง, movement — โดย master data ของคลังอื่น (เช่น คลังกลาง) ยังอ่านได้เพื่อให้ทำใบย้ายข้ามสาขาได้ แต่มองไม่เห็นยอดคงเหลือของเขา

## 4. ขั้นตอนสร้าง Role ใหม่ (Checklist)

1. **เตรียม catalog**: เช็คว่าเมนูที่ role ต้องใช้มีใน Menu Catalog ครบ
   - ไม่ครบ → **Import from App Menu** เลือกแอปนั้น → Import
   - รายการที่ติดธง **Needs Review** ให้เปิดมาเติม Data Model ก่อน (รายงานบัญชี = `account.report`)
2. **สร้าง role**: Roles → New → ตั้ง Name + Code (ภาษาอังกฤษ สั้นๆ เช่น `ap_branch`)
3. เปิด **Include Foundation** (ค่าปกติ) และ **Exclusive Membership** (สำหรับพนักงานทั่วไป)
4. **เพิ่มรายการสิทธิ์**: แท็บ Access Lines → **Add Multiple...** → ติ๊กเลือกรายการ → Add Selected → ปรับ Level รายบรรทัดตามต้องการ
5. **เช็ค Domain**: บรรทัดไหนมี Needs rule ติ๊กอยู่ ต้องมีค่าในคอลัมน์ Domain (override) เสมอ
6. **ใส่คน**: แท็บ Users with this Role → เพิ่ม user
7. กด **Apply — Build Access** → อ่านสรุปใน notification / แท็บ Last Apply Summary
8. **ตั้งคลังให้ user**: เมนู Users → เปิด user → แท็บ Warehouse Scope → เลือกคลังสาขาของเขา
9. **ทดสอบ** ตามข้อ 5 ก่อนปล่อยใช้จริง

**แก้ role ภายหลัง**: แก้ lines/users แล้วกด Apply ซ้ำได้เลย (ระบบ sync ให้ ไม่สร้างซ้ำ)

---

## 5. วิธีทดสอบ Role (ต้องทำทุกครั้ง)

1. ใช้ **user ทดสอบสะอาด**: สิทธิ์เริ่มต้นแค่ Internal User ไม่ถือกลุ่มมาตรฐานใดๆ
2. เพิ่มเข้า role (แท็บ Users with this Role) → Apply
3. login ด้วย user นั้น (หรือใช้เมนู superuser → Log in as) แล้วเช็ค:
   - เห็นเฉพาะไอคอนแอป + เมนูตาม whitelist ของ role
   - เปิดได้ทุกเมนูโดยไม่ติด AccessError
   - ค้นหา/เปลี่ยน filter แล้ว**ไม่เห็นเอกสารประเภทอื่น** (เช่น จากเมนู Bill ต้องไม่เจอ Invoice)
   - ข้อมูลสต๊อก/ใบย้ายเห็นเฉพาะคลังที่กำหนด

## 6. แก้ปัญหาที่พบบ่อย

### 6.1 เปิดหน้าจอแล้วติด AccessError "You are not allowed to access ..."
อ่านชื่อ model ใน error → เปิด catalog รายการที่เป็นต้นเหตุ → เพิ่ม model นั้นใน **Extra Read Models** → กลับไป Apply role อีกครั้ง

### 6.2 user เห็นเอกสารเกินขอบเขต (เช่น เมนู Bill เห็น Invoice ด้วย)
รายการนั้น Needs rule แต่ Domain ว่าง → เติม Domain ใน catalog (หรือ Domain override ใน line) → Apply ใหม่

หมายเหตุ: Domain กรอง**สิ่งที่เมนูแสดง** + ล็อกการ**สร้าง/แก้/ลบ**เท่านั้น ไม่ได้ห้าม "อ่าน" record นอกเงื่อนไข (user อาจเปิดเจอผ่านลิงก์/ค้นหาส่วนกลางได้ แต่แก้ไขไม่ได้) — เป็นการออกแบบหลังแก้บั๊ก 403 เมื่อ 20 ส.ค. 2026 เพราะถ้าบังคับตอนอ่าน rule จะลามไปโมเดลที่ inherits กัน (res.users←res.partner) จน user ล็อกอินไม่ได้

### 6.3 ไอคอนแอปซ้ำ / เมนูเพี้ยน
กด **Maintenance → Rebuild All Menus** — ห้ามแก้เมนูด้วย SQL ขณะ server รันเด็ดขาด

### 6.4 ติดตั้งโมดูลใหม่แล้วเมนูโผล่ถึงพนักงาน
โมดูล custom ที่เพิ่มเมนูต้องกำหนด `groups=` เสมอ ถ้าแก้โค้ดไม่ได้ ให้กด **Harden Standard Menus**

ระวังด้วยว่าเมนูมาตรฐานที่กั้นด้วยกลุ่ม "Technical Features" (เช่นแอป **Link Tracker**) จะโผล่ให้พนักงาน**ทุกคน**ทันทีที่เขาเปิด developer mode เอง (เติม `?debug=1` ใน URL ได้ ไม่ต้องเป็น admin) — Harden Standard Menus ครอบคลุมเคสนี้แล้ว และหลังอัปเกรดโมดูลมาตรฐาน (`-u`) รายการเมนูอาจถูกรีเซ็ตกลับ ให้กดปุ่มนี้ซ้ำ

### 6.5 ลบ role แล้วมีขยะเหลือ
กด **Maintenance → Remove Unused Groups**

### 6.6 user ที่เป็น admin เห็นเมนูซ้ำ 2 ชุด
ปกติ — admin ถือทุกกลุ่มจึงเห็นทั้งเมนูมาตรฐานและ whitelist ให้ทดสอบด้วย user สะอาดเท่านั้น

## 7. กฎเหล็กสำหรับผู้ดูแล

1. ใส่/ถอด role ให้ user ที่ **แท็บ Users with this Role → Apply** เท่านั้น
2. หลังแก้โค้ดโมดูล: **หยุด server → upgrade (`-u`) → start ใหม่** ห้าม upgrade ซ้อนขณะ server หลักรันอยู่
3. ห้าม SQL-delete เมนูขณะ server รัน — ใช้ Rebuild All Menus
4. Code ของ role ตั้งแล้วห้ามเปลี่ยน (group/rule ผูกกับ code)
5. ทดสอบด้วย user สะอาดทุกครั้งก่อนปล่อยใช้จริง
